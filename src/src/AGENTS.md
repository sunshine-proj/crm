# Backend Application Instructions

This directory contains the Symfony 8.1 application code (PHP 8.4): API controllers, request DTOs, Doctrine entities, repositories, and focused application services. Routes are declared with Symfony `#[Route]` attributes. The API returns JSON and persists CRM data to PostgreSQL through Doctrine ORM; invoice PDF downloads return `application/pdf`.

## Development

- backend is run in Docker container

## Structure And Conventions

- Think hard.
- Follow applicable PHP-FIG PSR recommendations, especially PSR-12 coding style and PSR-4 autoloading, and use Symfony 8 development best practices and conventions for application code.
- Apply object-oriented design throughout application code: keep responsibilities cohesive, encapsulate state and business rules, use constructor dependency injection, and avoid procedural or static business logic. Keep controllers thin; put reusable use-case logic in services when it grows beyond HTTP coordination. Follow the existing Symfony and Doctrine patterns without adding abstractions that do not clarify a real responsibility.
- Keep HTTP concerns in `Controller/`, typed data-transfer objects and validation constraints in `Dto/`, persistence mappings and domain invariants in `Entity/`, entity queries in `Repository/`, and cross-cutting use cases in services. Inject dependencies through constructors.
- Use Doctrine ORM and repositories for all runtime database reads and writes. Do not use raw SQL, direct PDO, or another persistence mechanism in application code. SQL in Doctrine migration classes is expected; keep schema changes versioned under `src/migrations/`.
- Use DTO objects for data exchanged across application-layer boundaries and for external API input/output. Controllers should map validated request DTOs into application operations and map results into response DTOs; do not pass request/response associative arrays between layers or expose Doctrine entities directly as API responses. Keep entities as persistence/domain objects, not transport objects.
- Keep response serialization and request field names compatible with the frontend. Current resources are clients, news items, projects, and tasks; timestamps are serialized in ISO 8601 form using snake_case response keys.
- For create/update actions, preserve the existing input-validation and status-code patterns (`400` for invalid input, `404` for missing records, `201` for creation, and `204` for deletion). Keep partial-update behavior consistent with the specific controller.
- Roles: `ROLE_USER`, `ROLE_FINANCE` (ledger, payables, invoice issue, receipts, cost visibility), `ROLE_INVENTORY` (purchase orders, goods receipts, dispatches, returns), `ROLE_DMS_ADMIN` (registry clerk) and `ROLE_ADMIN`, which inherits all of them (`role_hierarchy` in `security.yaml`). Finance and inventory do not inherit each other: purchase approval and goods receipt are separate duties. Use `ROLE_FINANCE` for finance data, `ROLE_INVENTORY` for anything that changes stock, and keep configuration, master data (warehouses, suppliers, clients), period control and recovery on `ROLE_ADMIN`; check `$this->isGranted(...)` rather than `getRoles()` so the hierarchy applies. New roles must be added to `SetUserRolesCommand::ASSIGNABLE_ROLES`. Notes may be changed only by their author or an administrator.
- Create/update/delete of clients, contacts, deals, projects, milestones, tasks, products, suppliers and warehouses is versioned automatically by `RecordRevisionListener` (list in `TrackedRecords`); do not track financial or append-only records. The listener also versions tracked rows that a database foreign key deletes (`CASCADE`) or detaches (`SET NULL`) with a deleted parent and links them to it (`cause_type`/`cause_id`), which `RecordRecovery` uses to bring them back; a new tracked entity with such a foreign key needs no extra code, but add a case to `RecordRecoveryTest`. Before allowing a delete that would destroy or orphan financial source data, extend `RecordDeletionPolicy` and return `409`.
- Modules: every API route belongs to core or one module in `App\Service\Module\ModuleCatalog` (route-name prefixes, plus `ROUTE_REQUIREMENTS` for routes that need two modules); `ModuleCatalogTest` fails for an unassigned route. `ModuleAccessSubscriber` answers `404` for disabled modules and `403` for role-hidden ones, so controllers need no checks of their own. Ask `ModuleGate` (`isEnabled()`, `isAvailableTo($key, $user)`, `setting()`) in services, scheduled jobs and cross-module side effects; change configuration only through `ModuleConfigurator` (dependency rules, validation, history). Disabling never deletes data. Automatic postings are skipped while `accounting` is off (`FinancePostingService::post()` returns null but still flushes).
- Who sees whose time is decided only by `TimeVisibility::scopeFor()` (`TimeScope`): `ROLE_FINANCE` (and administrators) see everyone, project managers see their projects, everyone else their own entries. Every time-entry read, report, export and workload query must go through it (`TimeEntryRepository::findVisible()`/`aggregate()` apply the scope in the query); cost stays `ROLE_FINANCE`-only. New time entries are built by `TimeEntryRecorder` (single, timesheet batch and timer), which owns validation and the rate snapshots.
- Time entries follow fixed correction rules: pending/rejected uninvoiced entries can be withdrawn by their author, approved uninvoiced entries can be reopened with a reason by an administrator or project manager (history in `TimeEntryEvent`), invoiced entries are immutable. Reminders are generated by `ReminderGenerator` (`app:reminders:run`); keep it idempotent via dedupe keys. Client tax identifiers and billing details are returned only to `ROLE_FINANCE`; never include them in unrestricted search or in `/api/history`. `LedgerReconciliationService` compares sub-ledgers with the GL; new auto-posting source types must be added to it.
- Inventory valuation (`InventoryValuationService`) must run inside the same transaction as the stock movement it values and is inert until the four inventory accounts are mapped; every stock path that changes quantity (receipt, dispatch, return, adjustment) must call it. Costs are integer minor units; use `proportion()` for rounding. Vendor bills linked to purchase orders go through `PurchaseMatchingService`. New valuation kinds need a posting source type in `LedgerReconciliationService`.
- Jurisdiction rules: tax on invoices and gapless numbering run only when `JurisdictionGate` finds an active `JurisdictionValidation` for the organisation country; never bypass the gate or hard-code rates in controllers. `InvoiceTaxService` and `TaxCalculator` own tax maths (integer minor units, basis points); `InvoiceSettlement` owns what is owed (gross total less credit notes less receipts) and invoice status; `DocumentNumbering::prepare()` must run before the issuing transaction and `allocate()` inside it. Issued invoices are immutable: correct them with `CreditNoteService`. Bank files are parsed by `Service/Bank/*` (reject DOCTYPE, integer amounts only) and never post to the ledger. New auto-posting source types must be added to `LedgerReconciliationService`.
- Organization structure (`OrgUnit`, `Position`, `Employment`, `Delegation`) drives document approval and acknowledgement. Ask `SubordinationService::chartOn()` for an `OrgChart` and use it for every "who reports to whom", "who heads which units" and "who deputizes" question; do not walk the tables by hand. Write-side invariants (single head post, one primary post at a time, no reporting cycles, subtree depth, archive/delete guards) live in `OrgStructureRules` and the entities; structure writes are `ROLE_ADMIN`, reads are open to all users. Org foreign keys are `RESTRICT`: archive used units and positions, and end employments, rather than deleting them.
- Document registry (`App\Service\Dms`): `DocumentAccess` is the single read/manage/edit rule and `DocumentRepository::search()` mirrors its read rule in the query; keep the two in step. Route use cases through `DocumentService` so every change records a `DocumentEvent`. Registration numbers come only from `RegistryNumbering` (`prepare()` before, `allocate()` inside the registering transaction). Versions are immutable; registered documents are archived, never edited or deleted. Answer `404` for documents the caller cannot read. `ROLE_DMS_ADMIN` (registry clerk) owns types, registration and archiving; `ROLE_ADMIN` inherits it. Files go through `DmsFileStorage` (content-detected MIME allowlist, SHA-256), stored under `var/project-documents/dms` so the existing backup covers them. Changes to numbering or search must also pass `scripts/verify-dms-e2e.sh` on PostgreSQL.
- Approval (`ApprovalService`, aggregate `ApprovalRoute` → `ApprovalStage` → `ApprovalStep`): change route state only through `ApprovalRoute` methods, inside the route-row lock (`decide`, `withdraw`), and log each action as an `ApprovalAction`. Approve/sign assignees must pass `OrgChart::isSuperiorOf(assignee, author)`; reviews need a position; the author never participates; forwarding goes to the assignee's subordinates only; deputies act through `OrgChart::deputyFor()` and are recorded as `on_behalf_of`. Participants (and active deputies) may read the document: keep `DocumentAccess::canRead()` and the `EXISTS` clause in `DocumentRepository::search()` in step. Approval reminders live in `ReminderGenerator` with `approval_step:<id>` dedupe keys.
- Acknowledgement (`AcknowledgementService`, `AcknowledgementAudience`; entities `AcknowledgementRequest`, `AcknowledgementRecipient`): senders are unit heads for their `OrgChart::managedUnitIds()` subtree, or `ROLE_DMS_ADMIN` organization-wide (`scopeOf()` returns `null`); only `Document::ACKNOWLEDGEABLE` documents can be sent. Resolve targets only through `AcknowledgementAudience` (it validates scope and snapshots unit and position per recipient); never recompute who was asked from today's structure. Confirmation is personal (no deputies) and runs under a row lock; the sender and clerks control a request, heads of a recipient's recorded unit supervise (remind, excuse) and see only their part. Recipients may read the document: keep `DocumentAccess::canRead()` and the second `EXISTS` clause in `DocumentRepository::search()` in step. "Viewed" is set when the requested version's file is served (`DocumentController::versionFile`). Joiners are added after employment changes and by `app:reminders:run`; reminders use `ack_recipient:<id>` dedupe keys, manual reminders `ack:<id>:remind:<date>`. Notifications for DMS work go through `DmsNotifier`.
- Records management: lifecycle transitions (`takeEffect`, `supersede`, expiry `archive`) run only through `DocumentLifecycle` (`app:dms:lifecycle`) and `DocumentService::supersedeReplacedBy()`/`archiveAs()`; flush a status change before querying on it. Registered documents are never deleted: the only way content goes is `DisposalService::approve()` (archived, past `retainUntil()`, no legal hold, approved by an administrator other than the proposer), which keeps the row as a `disposed` tombstone and deletes files only after commit. Check `isOnLegalHold()` wherever something can be deleted. Every user-visible document action is a `DocumentEvent` (views once per person and day via `recordView`); `DocumentAudit` merges them with `ApprovalAction` rows, so new actions need no extra audit wiring. Uploads go through `DmsFileStorage::store()`, which runs `ClamAvScanner` when `DMS_CLAMAV_DSN` is set; `ScannerUnavailable` must answer 503, never store the file.
- Authentication is stateless JWT for `/api`; login is public. Authorization is resource-specific: projects/tasks require `ROLE_USER`, client writes require `ROLE_ADMIN`, and news-item edits/deletes are restricted to the owning user. Inspect the controller attributes and `config/packages/security.yaml` before changing these rules.
- When changing entity mappings, add or update a Doctrine migration under `src/migrations/`; do not rely on schema auto-update. Keep migration changes consistent with the entity and existing database history. Use Doctrine migrations for schema changes, not as a way to perform unversioned application data access.
- `ApiAuditSubscriber` writes every state-changing API request and every refused request (401/403) to the `audit` channel with actor, route, numeric route parameters and status; it never logs bodies or query strings. Controllers add domain events on top through `monolog.logger.audit` (for example client reads, which flag disclosure of restricted fields). Preserve these events and never log credentials, JWTs, request payloads or other secrets. `/api/login` throttles failed attempts through the `login` rate limiter.
- Invoices are currently editable drafts linked to a client and project, with task and additional-cost line snapshots, explicit EUR/GBP/USD currency, server-calculated integer minor-unit totals, and PDF export through Dompdf. Add all invoice schema changes through Doctrine migrations and keep PDF output escaped and independent of remote resources.
- Never use floating-point arithmetic for invoice amounts. Validate decimal strings at the API boundary, calculate in integer minor units, and require a currency when filtering by amount. Do not imply that a draft PDF is a legally issued invoice.
- Do not put frontend code or container configuration in this directory; those have separate scopes in `frontend/` and the repository root.

## Testing And Verification

Automated tests are required for all project-owned backend behavior. Aim for complete coverage of production code, including successful flows, validation failures, missing records, authorization, and edge cases. Add regression tests with every behavior change; use unit tests for isolated rules and integration/API tests for persistence, HTTP, and security behavior. Use a coverage report to find and close gaps, and do not claim full coverage without a report.

PHPUnit 12 is configured with unit and SQLite-backed integration and HTTP flow tests under `tests/`; run them with `php bin/phpunit` from the backend project directory, or `docker compose run --rm --no-deps php php bin/phpunit` from the repository root (run `composer install` first: `vendor/` is not committed and the functional tests need the dev packages). HTTP tests extend `tests/Functional/ApiTestCase.php`, which provides one user per role, `openLedger()`, `assertInvalid()` and `auditRecords()`. Coverage runs with `composer test:coverage` and `composer test:coverage:check` fails below 90% of lines (pcov; needs an image built from `docker/php/Dockerfile`). The last measured figure is in the README; re-measure before quoting one, and do not claim complete coverage. Every API route's required role is pinned in `tests/Unit/Security/ApiAccessPolicyTest.php`; classify new routes there. Do not describe syntax checks as test coverage.

Run Symfony commands from the backend project directory (`src/` at the repository root), for example `php bin/console debug:router` or `php bin/console doctrine:migrations:diff`. In the containerized environment, use `docker compose exec php bin/console ...` from the repository root. Run `php -l path/to/changed.php` for a quick syntax check, in addition to relevant automated tests. Do not claim a migration was applied unless it was explicitly executed against the intended database. SQLite does not enforce the foreign-key and locking behaviour PostgreSQL does, so changes to migrations, cascades, numbering or concurrency must also pass the repository-root scripts against PostgreSQL: `scripts/verify-migrations.sh` (self-contained) and the `scripts/verify-*-e2e.sh` checks (need a running API on a disposable database).
