What works
You can set it up and use it like this:


pip install -e ".[dev]"
aiopt init && aiopt analyze && aiopt cache update
aiopt context search "authentication"
aiopt context build --task "Implement password reset" --max-tokens 4000
aiopt trust && aiopt task run validate
aiopt metrics
Project analysis: produces the three JSON metadata files. Repeated runs are byte-identical. It supports Python and JavaScript/TypeScript manifests, and Makefile targets.
Cache: incremental SQLite index. A no-change update rehashes 0 files. It detects renames, recovers from an interrupted update, and rebuilds a corrupt cache automatically.
Search and context packages: FTS5/BM25 search, profiles, and token-budgeted Markdown or JSON packages.
Tasks: run only after you've reviewed and trusted the project, and each step is checked against an allowlist.
Metrics: estimated token figures are always labeled as estimates.
Performance on 10,000 synthetic files beat the PRD's provisional targets:

Operation	Result
Initial index	0.85 s
No-change update	0.17 s
Search	0.17 s
Context package	0.18 s
Testing
I broke six security-critical behaviors on purpose (shell denylist, trust check, process-tree kill, rehash skipping, sensitive-file filter, working-directory containment). The tests caught every one.
That check and the tests turned up five bugs, now fixed. The main one: the analysis output differed between runs because the tool's own directory was being counted.
The tests ran entirely in temporary directories. Your real ~/.config and ~/.local/state were not touched.
What to know before relying on it
Allowed tools are not sandboxed. Running pytest means running the project's test code, so use a container for repositories you don't trust. This is documented in docs/usage.md.
aiopt trust can be answered by a script. It asks for interactive confirmation and has no bypass flag. An AI agent with shell access could still pipe an answer, so don't auto-approve that command in the assistant.
The core premise is still untested. Whether assistants actually use this output instead of their own search is exactly what Phase 0 is for.
Only Linux was tested. Windows is best-effort.
Search quality depends on keywords. --task extracts keywords with no LLM. In small corpora, BM25 scores are near zero, so I scale package scores per query so profile weights can reorder results.
Decisions I made
I recorded these in PRD §14:

The default allowlist covers Python tools only (pytest, ruff, mypy). npm and make must be added by you, because package scripts and Makefile targets run repository-defined code.
The first index is a baseline, so the code-review profile doesn't list the whole repo as changed.
--output must stay inside the project directory.

MCP tools: aiopt mcp serve runs the 9 tools. They call the same service functions as the CLI, so trust, allowlist and timeout rules are identical.
Idempotent and reversible: repeat installs change nothing, and uninstall restores the files it touched exactly. This is tested byte-for-byte.
Existing config is protected: your own files, existing server entries, and JSON files with comments are never overwritten or rewritten. They're reported as skipped, with the manual snippet.
One source of truth: instructions and skills are written once and placed per provider. If CLAUDE.md imports AGENTS.md, the block goes in AGENTS.md, and Codex shares it.
Findings along the way
MCP SDK hides tool errors. It reduces exceptions to "Error executing tool", so an agent would never see "project not trusted, ask the user to run aiopt trust". Expected errors are now passed through verbatim.
aiopt trust needed hardening. A Claude Code deny rule only matches the command text, so aiopt --json trust would slip past it. aiopt trust now refuses to run without an interactive terminal, so run it yourself in the VS Code integrated terminal.
Assistant config files were being indexed and polluting search, so .claude/ and .codex/ are now excluded by default.
Permission rules were checked against the current docs. I used a documentation-checking subagent for the Claude Code formats, and web searches for the VS Code and Codex ones. Allow rules cover read-mostly commands and the exact command aiopt task run validate. aiopt trust is denied. Other task runs, --allow-destructive and MCP run_task still prompt.
All ten deliberate breakages of safety behavior (for example, overwriting unmanaged files or letting MCP run destructive tasks) are caught by the tests.

What to know
Not tested against live Claude Code, Copilot or Codex. I verified the file formats against their docs and tested everything on our side, including a real stdio MCP session. After installing, check /mcp and /skills in Claude Code, and the tools list in Copilot's Agent mode.
MCP SDK version: it's tested against mcp 2.x. A fallback for 1.x exists but is untested.
Assistant-side permission rules are your real control. The trust record is a file in ~/.local/state, so an agent that can write there could still bypass the trust prompt.

The measurement tooling is implemented: Phase 0 (protocol and retrieval baseline) and Phase 5 (reports and usage import). All 350 tests pass, ruff is clean and strict mypy reports no issues.

I haven't run the assistant A/B comparison itself. It needs real Claude Code sessions with and without the integration, so whether assistants actually spend fewer tokens or tool calls with aiopt is still unmeasured.

What was added
aiopt bench run SPEC scores retrieval on labeled cases, using recall@k, MRR and size comparisons against honest baselines (whole repo, files matching a query term, top-k files read in full). --min-recall makes it exit 3 when below a threshold, so it works as a CI gate. Benchmark runs don't touch your real metrics.
aiopt usage import claude reads real token and tool-call counts from Claude Code session logs. It stores counts and tool names only, never message content.
aiopt usage label and aiopt usage report compare labeled groups such as baseline and aiopt. They warn when a group has fewer than 5 sessions.
aiopt report combines local metrics, the latest benchmark and imported usage, with every figure tagged by source (estimate or provider-reported).
docs/benchmark.md covers how to write cases and a step-by-step A/B protocol. It also says to write your decision rule before running anything.
What the testing found
Usage is repeated across the lines of one API message. Without deduplicating by message id, tokens would be overcounted several-fold. I checked the parser against the real log of this session (91 messages at the time, matching an independent count).
Subagent usage lives in separate files. The importer was silently ignoring it, which would make a delegating session look cheaper than it was. It now merges those logs.
Adoption detection was too loose. echo aiopt and grep aiopt would have counted as aiopt use. Only commands that actually run the executable, or an aiopt MCP tool call, count now.
I mutation-tested the safeguards: double-counting, loose adoption detection, hidden labels, a dropped small-sample warning, and ignoring depth in recall. All are caught. (My mutation check for "benchmark pollutes metrics" initially hit the wrong function. I re-ran it correctly and the test does catch it.)

Benchmark results on this repo
I wrote 16 cases before seeing any results. On 70 files: search recall@5 is 84%, and 13 of 16 cases found all expected files.

The package does not beat plain search. At equal depth (about 15 items) the package reaches 94% against 97% for plain search. Its value has to come from bundling conventions, dependencies and validation commands, which only the A/B comparison can show.
Results move with the corpus. Adding two files shifted MRR from 0.66 to 0.61 and package recall from 100% to 94%.
One genuine weakness. Documentation is capped at 5 items per package, so a skill file lost its slot to the new guide. I left it unfixed on purpose, because tuning against a 16-case benchmark would overfit it. This is recorded in the docs.
This is one small repo, and I wrote both the code and the cases, so treat the numbers as a baseline, not a general claim.
